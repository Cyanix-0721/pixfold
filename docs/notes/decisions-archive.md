9. ~~**拖拽落地方式**：是否需要"拖动中实时让位"的观感？~~ —— **⚖️ 已改判(2026-10-14):改为「实时让位」,

   自动显示新的位置而不是生硬的悬浮在某个卡片或行上」。

    **当前有效裁决(2026-10-14 起)**:
    - **实时让位**:拖动中其他卡片/行**立刻让位**,被拖项以半透明占位落在新位置;不再只做"目标格高亮"。
    - **界面实时变,数据只提交一次**:拖动中只重排**本地展示顺序**(`dragItems`),`onMoveTo` **一次都不调**;
      松手时按最终索引提交**一次**。这条分工是关键 —— 旧裁决担心的不是"重排"本身,而是"拖动中不断提交":
      那会让 `PageOrderState.manualIds` 灌满、撤销记录被污染,指针微动时顺序来回换位。
    - **收敛性(抖动死区的解法)**:目标格由**格矩形包含判定**(`findContainedSlotAt`)得出,
      重排后被拖项已占据指针所在格 ⇒ 下次事件算出的目标 == 自身 ⇒ **立即稳定**;
      指针落在格/行**缝隙**时判为 `null`(保持原目标不动),**刻意不兜底到"最近格中心"**;
      只有当指针**移出容器**(手指滑出网格下沿进底部动作栏)时才退化为最近格,否则贴边自动滚动期间让位会停摆。
    - **跟手浮层保留**(2026-09-25 那半条仍有效),由 `ui/components/DragGhost.kt` 承担。
    - **旧"目标格高亮"已移除**:`isHovered` / `HoverBorder` / `primaryContainer` 高亮分支全部删除
      (实时让位下"卡片真的挪过去了"取代了"高亮它"),`DraggableThumbCard`/`ThumbRow` 参数相应精简。
    - **实现位置**:`ui/components/DragReorderGrid.kt` 与 `DragReorderList.kt`;纯判据抽为
      `resolveReflowTarget(...)`(容器内命中格 / 容器内缝隙 ⇒ null / 容器外 ⇒ 最近格),可离线单测。
    - **自证**:变异 M10–M17(8 组;M15"浮层尺寸改实时取"存活,已按 §7.4 改掉该断言口径并写明);
      四道闸门绿(app 476 / domain 483 / lint 零告警)。**真机核对已通过(2026-10-15,用户亲测)**:
      用户逐字「回主页重置正常,**拖拽也可以但是缺少动效不够好看**」⇒ 功能达成,动效另开(见下)。
    - **✅ 让位动效已落地(2026-10-15/16)**。用户 2026-10-15 要求补动效(原为重排瞬时生效、无过渡),
      真机复测后又反馈「动画有点慢,而且拖拽到边缘的时候会抽搐」⇒ 分两轮修完,详见下条。
    - **动效实现**:`ui/components/DragReorderAnimation.kt` 的 `DragReorderPlacementSpec` ——
      `spring(dampingRatio = DampingRatioNoBouncy, stiffness = StiffnessHigh, visibilityThreshold = IntOffset.VisibilityThreshold)`,
      经 `Modifier.animateItem(fadeInSpec = null, placementSpec = …, fadeOutSpec = null)` 挂载。
      三个参数各有实测依据:① **spring 而非 tween** —— 位移动画会被连续重启(指针每跨一格一次),
      spring 从当前速度继续、tween 每次从 0 速度起步,且 foundation 的 `InterruptionSpec`
      **只对非 `SpringSpec` 生效**(传 tween 会被顶换成 `spring(1.0/400)`,比 Medium 还慢);
      ② **`StiffnessHigh`(10000) 而非 Medium(1500)** —— 用户「有点慢」的量化依据:72px 一格
      时 t90 从 100.4ms 降到 38.9ms,连续重启下的稳态追踪滞后从 **196.4px(≈2.73 格)** 降到
      **54.7px(≈0.76 格)**;③ **必须显式传 `visibilityThreshold`** —— 不传时走
      `DefaultSpringAnimations` 分支用 `DefaultDisplacementThreshold = 0.01f`,比库默认的
      `IntOffset.VisibilityThreshold = (1,1)` 精细 100 倍,动画尾巴明显更长。
      `fadeInSpec`/`fadeOutSpec` 传 `null` 且**只在拖动期间挂载**:只要任一 spec 非 null,
      项进出视线时就会被留在组合树并量成 0 尺寸,污染取 `min()` 的既有几何断言
      (实测常挂即便三档全 `snap` 也会让 2 条不涉及拖拽的既有测试变红)。
    - **「边缘抽搐」的根因与修法(本轮最有价值的一条)**:命中判定的格几何原先由各 item 的
      `onGloballyPositioned` **累积**(`slotBounds: Map<Int, Rect>`),而 `animateItem` 的位移动画
      施加在 item 自身的 `graphicsLayer` 上 —— **`onGloballyPositioned` 读到的是飞行途中的矩形**。
      于是「指针已落在新占位的格内,却按旧矩形算」⇒ 反复换位 ⇒ 动画反复重启 ⇒ **自我维持的抖动**。
      修法 = 抽出纯函数 `layoutSlotBounds(visible, containerTopLeft, padLeft, padTop, headerOffset)`,
      **每次由 `gridState.layoutInfo.visibleItemsInfo` 现算逻辑几何**,与动画解耦
      (公式 `rect = containerTopLeft + contentPaddingTopLeft + info.offset`,size 取 `info.size`;
      前导 header 项按 `headerOffset` 跳过并减去,否则逻辑下标整体错位)。
      ⚠️ **不能靠「把 `animateItem` 挪到内层」或「外层再包一个 Box」回避** —— 实测前者让动画
      **静默失效**(不报错、就是不动),后者读数依旧(动画图层挂在 item 根上)。
      ⇒ **教训**:凡"读界面几何做命中判定"的地方,都要问一句「这个读数会不会被动画污染」。
    - **自证**:`LayoutSlotBoundsTest`(5 例,含容器左上角 + padding 计入、header 偏移、空列表)
      + `DragReorderAnimationSpecTest`(钉规格,并如实记录三条**无杀伤力**的观测路径:读语义树几何 ❌
      —— `animateItem` 施加在自身图层上、`boundsInRoot` 不计入节点自身变换;逐帧比像素 ❌ ——
      主要反映跟手浮层噪声,`snap` 与 `spring` 读数一模一样;断言"两帧有变化" ❌ 更弱)
      + 变异 M1–M6。**真机核对已通过(2026-10-16,用户亲测)**:用户逐字「**效果可以**」,

      **无自我维持抖动**。

12. ~~**空间不足的提示阈值与引导方式**~~ —— **✅ 已关闭(2026-10-19 晚,D2b 平台层接线时定档)**。
    阈值 = `SpaceThreshold.Percentage(marginPercent = 10)` + `safetyMargin = 32 MiB`(`SafPackExecutor` 内部常量)。
    选百分比而非绝对值的理由:CBZ 输出体积 ≈ 原图总和(ZIP 对已压缩的 JPEG/PNG 再压收益 < 2%),10% 随卷大小自然伸缩;
    32 MiB 兜 ZIP 目录区 + `ComicInfo.xml` + provider 写入缓冲与前后的元数据更新 —— 「刚好够」时失败会发生在**写到一半**。
    提示形态 = **执行前阻断**(`PackBlocker`)+ 可行动读数(`humanBytes` 后的「还差 X(当前可用 Y)」),不是事后报错。
    同一处另加了**输出名撞车阻断**(见 §9 D2b):两者都是「改完就能立刻重试」的单点问题。

15. ~~**[P5 真机核对中发现,2026-09-19] 批量设置是否应被视为"逐项例外"?**~~ —— **已定(2026-09-25)**:
   采用**备选语义(批量≠例外)**。批量写入后**清除该字段的逐项例外标记**,故同一字段可反复批量覆盖;

16. ~~**[P7 走查中发现,2026-09-19] 清洗设置可能"改了看不到效果",是否需要提示?**~~

    **✅ 已裁决并实施(用户 2026-09-19 选「方案 A」:加静态示例行)**

    **背景与一次归因纠正**:初记时我写的是"默认方案不含原文件名,所以替换字符不可见"
    —— **实测推翻(同日)**:默认方案(根目录名 + 图片序号)下把根目录名设为 `旅行:照片`、
    替换字符设为 `#`,输出为 **`旅行#照片_001.jpg`**,**替换字符在默认方案下可见**。
    **准确条件**:非法字符**不只来自原文件名** —— `RootDir`(用户手输,默认启用)、
    `Prefix`/`CustomText`(用户手输)、`RelDir`/`OrigName`(来自文件系统)都可能含非法字符。
    故"改了没效果"的**准确条件**是:
    > 输出中**所有已启用组件**的文本与扩展名**都不含非法字符**。

    典型情形 = 默认方案 + 根目录名合法 + 原文件名非法(而 `OrigName` 默认**未启用**)。

    **裁决结果:方案 A(加实时示例行)**,已在「自动清洗」ⓘ 对话框内实施:

    > `示例：封:面?.jpg → 封_面_.jpg`

    **为什么选 A 而非"条件提示"(方案 B)**:
    1. 用户困惑的**根源是"不知道这个字符做什么"**,一句具体示例即可消除 —— 这本就是 ⓘ 的职责;
    2. B 的提示在真实数据下**很少触发**(根目录名/原文件名常含非法字符),
       等真看到提示时用户多半已经困惑过了;
    3. B 需新增领域判定函数 + 一个状态相关分支,而**收益场景窄**;A 零状态依赖。

    **实现要点**:
    - **示例值由真实的 `sanitizeName` 算出,不写死字符串** ——
      硬编码的话,一旦清洗规则变化(改非法字符集/改替换逻辑),说明文字就会与真实行为不符,
      而那种"文档说谎"极难被发现。让示例**结构上不可能说谎**。
    - 示例输入选 `封:面?.jpg`:同时演示"非法字符被替换"与"**扩展名也参与清洗**"(§6.1 第 7 步)。
    - 随状态三态联动:替换字符 `_` → `封_面_.jpg`;改为 `*` → `封*面*.jpg`;
      **留空** → `封面.jpg`(与「留空 = 直接删除非法字符」的说明一致)。

    **三层自证**:
    - **领域层**:复用既有 `sanitizeName` 单测(默认值同源、留空=删除)。
    - **UI 层**:`ReplacementFieldTest` 新增 3 项 —— 示例存在、**随替换字符变化**、
      **示例等于领域函数结果**(钉死"示例 = 真实清洗结果")。UI 合计 241 项。
    - **真机核对**:实例行真机可见;改 `*` 后示例实时变为 `封*面*.jpg`;
      留空后示例变为 `封面.jpg` 且说明切为「留空 = 直接删除非法字符」。无崩溃。

    **变异验证 2 组,均捕获**:
    - 把示例**写死**为固定字符串(即"文档说谎"风险)→ **2 项失败**;
    - 示例输入改为不含非法字符的 `封面.jpg`(演示不出效果)→ **3 项失败**。

18. ~~**[第 9/10/14 条那轮真机核对中新发现] 拖拽无法跨视口 —— 30 张图时从第 1 张拖到第 30 张物理上不可能。**~~
    —— **已修(2026-09-25 实现;2026-09-26 真机核对通过)**。

    **⚠️ 初判根因是错的,实测定为另一条。** 初记写的是"① `DraggableThumbCard` / `ThumbRow` 的
    `onDrag` 里 `change.consume()` 阻断了 LazyGrid/LazyColumn 接收手势",探针实测**不成立**
    —— `change.consume()` 只阻止 Lazy **自己**滚动,并不杀死手势。真因是:

    ① **拖拽手势挂在卡片上(`pointerInput(item.id)`),而卡片是 Lazy 的子项** —— 一旦滚得够远,
       被拖的那张卡离开视口,`LazyGrid` / `LazyColumn` 把它销毁,挂在它身上的 `pointerInput`
       随之被取消,`onDragEnd` **永不触发** ⇒ 跨视口拖拽**物理上不可能**。
       (探针按触边事件数读活性:4 次触边仍活、16 次触边后浮层消失 = 手势已死。)
    ② 全组件**没有任何边缘自动滚动**(`scrollBy` / `animateScroll` 零命中),也没有"拖到边缘就翻页"的替代路径。

    **修法(两步缺一不可)**:
    - **把手势从卡片上移到不滚动的容器 `Box`**(`DragReorderGrid.kt` / `DragReorderList.kt`),
      卡片只负责显示;命中判定由容器拿 `slotBounds` 反查(`findContainedSlotAt`)。
      这样被拖的卡即使滚出视口被销毁,**手势依然活在容器上**。
    - **拖动期间把滚动权交给程序**:Lazy 加 `userScrollEnabled = draggingIndex == null`
      (探针实测:不交出滚动权时 Lazy 在 Main 阶段先接到事件、立刻转成 `cancel`,手势长度 2;
      交出后手势完整走完,`events=12`、收尾是 `end`),滚动改由 `EdgeAutoScroll.kt` 的
      `edgeAutoScrollStep(...)` + `scrollBy` **按每个 `onDrag` 事件驱动**。
      边缘带宽 72dp / 基础步长 14dp / 连续触边加速上限 4×。

    **为什么是事件驱动而不是帧循环/定时器**:帧循环在本仓库**离线不可驱动**且会挂死测试套
    (无条件 `while(true){ withFrameNanos{} }` ⇒ `setContent`/`waitForIdle` 永不返回,
    `java.lang.InterruptedException at Builders.kt:94`;`autoAdvance = true` ⇒
    `OutOfMemoryError: Java heap space`;`advanceTimeByFrame()` 不恢复续体)。**代价(有意取舍)**:
    指针在边缘完全静止时不继续滚动 —— 真机手指会抖,叠加加速后长距离仍可达。
    归档 Flutter 原型同样用长按起拖「避免与滚动冲突」,同向。

    **判据(真机可证伪)**:点开 `旅行照片`(30 张,10 行、可视约 5 行),按住第 1 张往屏幕下缘拖 ——
    列表**跟着滚**,能在**一次手势内**拖到第 30 张并提交落点。

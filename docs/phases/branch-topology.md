## D1.1 分支拓扑与阶段切分(2026-09-16 用户决定)

> 背景:换栈后 D1 需从零重建(§9 D1 执行注),原型代码改在**本仓库的阶段分支**开发,
> 不再放仓库外目录(2026-09-13 的整树丢失教训见 §12.7)。本节固化拓扑,避免"每阶段一分支"被各人各理解。

**分支拓扑**:

```text
ready ──► dev                          ← ready 整合进 dev,dev 成为开发主线
            ├─► d1/p1 ─┐
            ├─► d1/p2 ─┤  每阶段从 dev 开一个分支
            ├─► …      ├─ 阶段完成 → 合回 dev + 在 dev 回写文档 → 删阶段分支
            └─► d1/p7 ─┘
                  │
                  ▼
            dev = 完整测试版(D1 验收清单 20 项全绿)
                  │
                  ▼
                main ──► 发 release ──► 此后开发继续走 dev
```

- 阶段分支**从 `dev` 开、合回 `dev`**,**不直接进 `main`**;`main` 只在 D1 全绿后接收一次合并并打 release。
- 阶段分支完成时**先在 `dev` 上回写文档**(状态、踩坑、验收进度),再删分支。
- 原型代码**永不进 `ready`**;`ready` 保持为设计文档线。
- 提交与推送:**每阶段完成即提交**;push 由用户自行处理(用户 2026-09-16 约定)。

**用户 2026-09-18 追加的两项设计决定**:
1. **根目录名跟随集合** —— 此前命名结构整体是批次级,导致切到 `扫描件` 集合后建议名仍是
   `旅行照片_005.png`。改为:默认取**当前集合**的 `rootDirName`,用户显式改过则记为**逐项例外**
   且切集合不被冲掉(即 HANGOFF §2 约束 4「批次统一 + 逐项例外」)。
   用独立可空字段 `rootDirNameOverride` 表达"是否覆盖",而非把集合名写回 scheme
   (后者分不清"跟随的默认值"与"用户输入")。**组件/分隔符/补零/扩展名仍是批次级**。
2. **清洗说明改用圆形感叹号图标 + 点击展开**(见上表 #2)。

**顺带修掉的功能缺口(用户提问"支持预测性返回手势了吗"——此前不支持)**:
真机实测:在"步骤2 命名结构"按返回会**直接退出应用**,用户丢失当前位置;
项目此前**完全没有返回处理**。修复后层级为
`预览 → 工作流A(步骤2) → 工作流A(步骤1) → 首页 → 退出`;
`WorkflowASteps` 用**单个** `BackHandler` 按层级决策(而非"非首步才启用 + 靠外层兜底"),
使注册始终 enabled —— 系统据此知道"返回有去处",预测性返回才会走应用内后退。
Manifest 显式 `enableOnBackInvokedCallback="true"`(targetSdk 33+ 默认,写明意图);
该属性触发 lint `UnusedAttribute`(minSdk 低于 33 时),以 `tools:targetApi="33"` 标注。
**2026-09-22 注**:minSdk 已由 24 提到 30(见 §12.6),该注解**仍然必要**(30 < 33),故保留。
**2026-09-25 更新**:minSdk 已由 30 再提到 **34**(见 §12.6)⇒ 34 ≥ 33,该 `tools:targetApi="33"`
注解与 `xmlns:tools` 声明**一并删除**。`enableOnBackInvokedCallback="true"` 本身保留不变。

> **⚠️ 如实记录的范围与局限**:
> 1. **超长(第 10 项的四类之一)未在真机复现** —— 真机上让 `baseName` 达到 181 字符需长文本输入,
>    操作成本高且 `adb input text` 易被输入法干扰。该项由**领域单测**钉死
>    (`too long triggers only above 180`、`chinese counts as one unit`),
>    **不计入真机已核对的范围**。其余三类(重名/跨目录重名/非法字符)均已真机复现。
> 2. **`fillType="evenOdd"` 的作用曾被我判断错** —— 原以为"漏了它就看不见感叹号",

**四条设计取舍(值得记住)**:

1. **"两次确认"做成数据而非 `if` 嵌套** —— 序列驱动,于是"恰好两次""先通用后危险""取消归零"

2. **危险确认逐项进行,不合并成"全部确认"** —— 否则一次点击放行多个不可恢复动作。
3. **危险确认顺序固定**(`DANGER_ORDER`),不随 `Set` 迭代顺序变化 ——

**⚠️ 走查环境教训(新增,已并入 §12.5)**

1. **设备休眠会伪装成"应用出问题"**:走查中两次 dump 到的是**通知栏/锁屏**
